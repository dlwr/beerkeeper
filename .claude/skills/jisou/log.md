# 自走ログ

回ごとの経過は書かない（PR は git 履歴で追える）。200 行以内に保つ。

## もう出さない候補

- 終了後の参加・キャンセル: 終了したイベントでは受け付けないと決めた（#68）。開催中は許す
- テキストメールの HTML エスケープ: `text/plain` のテンプレートはエスケープされず、`&` はそのまま届く（確かめ済み）

## 測って分かった前提

- RunSpecs は 1 分ほどで終わる
- 本番 DB は Fly ボリューム上の SQLite で、マイグレーションはマシン起動時の `db:prepare` で流れる。デプロイが失敗するとマイグレーションだけ流れた状態にはならないが、戻すにはボリュームの復元が要る

## 踏んだ罠

- クラウドの初期イメージには `.ruby-version` の Ruby が無く、`/opt/node22/bin` に Chrome と版の合わない chromedriver がある。環境の setup で `bin/cloud-setup` が片付ける。`ruby -v` が違えば `bash bin/cloud-setup` を流して `. /etc/profile.d/ruby.sh` する
- system spec の Chrome はパスワード漏えい検知のダイアログで次のテストの送信を止める。`spec/support/capybara.rb` で `profile.password_manager_leak_detection` を切ってある
- クラウドのセッションでは、ダウンロードした外部バイナリ（Litestream など）の実行が権限で拒否されることがある。オーナーが許可すれば動く（flyctl は `fly.io/install.sh` で入った）。ただし Fly のトークンは環境に無く、`fly secrets list` などは使えない
- 1 つの作業ブランチで PR を続けて出すと、squash マージ済みの古いコミットがリモートに残って push が弾かれる。force push はせず、リモートのブランチをマージしてから push する
- rspec を流すと `app/assets/builds` が消えることがある。開発サーバーで画面を見る前に `bin/rails dartsass:build` する
- PR 本文に `Closes` を2つ並べると片方しか閉じないことがある。マージ後に issue の状態を確かめる
- CI とクラウドの test DB にはシード（`mitakarb` のイベントなど）が入っている。全件を数える・並べるテストは自分で作った行に絞る
- PR 本文の `Generated by` フッターは、REST で消してもサーバー側で付け直される
- `gh api search/issues` は `is:issue` か `is:pr` を q に入れないと 422 になる
- ログインが要るコントローラーには `before_action :require_login` を自分で付ける。`authenticate` は `current_user` を入れるだけ
- 作業ブランチは1本なので、PR の CI 待ちの間に次の issue は `wip-*` のローカルブランチでコミットし、マージ後に main を取り込んでから cherry-pick して push する。リモートのブランチ削除はプロキシで拒否される
- `bin/cloud-setup` の `db:setup` が test DB の外部キーで落ちることがある。`RAILS_ENV=test bin/rails db:drop db:create db:schema:load` で作り直せば rspec は通る
- `bundle exec` が見つからないときは `. /etc/profile.d/ruby.sh` を同じコマンドの中で読む（シェルの状態は呼び出しごとに消える）
- steep の `lenient` は未定義メソッドを見逃す。`Steepfile` は `default` にしてある。手書きの型は `sig/app/`、生成物は `sig/rbs_rails/`（モデルや関連を変えたら `bin/rails rbs_rails:all`）
- `rbs_rails` は開発 DB が migrate 済みでないと失敗する。開発 DB を migrate すると `db/schema.rb` の列順が崩れることがあるので、`db:drop db:create db:schema:load` してから migrate し直す
- steep は `has_many` のスコープの lambda の self を自クラスとみなす。別クラスのスコープを呼ばず `where(...)` で書く（クラス起点にすると join 時の別名に追従しない）。concern の `included do` も型が付かないので、関連はモデルに直接書く
- 本番の挙動は `SECRET_KEY_BASE_DUMMY=1 RAILS_ENV=production bin/rails runner ...` で手元でも見られる（DB には触らない範囲で）
- `participation` の factory は `user` を作らない。`create(:participation, event:)` だけだと検証で落ちるので `user:` を渡す
- `event_cancellation` の factory は存在しないクラスを指していて使えない。中止は `event.cancel` で作る
- request spec でページの一部だけを確かめるときは見出しで区切る（イベント名に「中止」などの語が入ると本文全体の include では区別できない）。`travel_to` の中で遅延の `let` を初めて呼ぶと、作成日時もずれる
- 否定の matcher（`define_negated_matcher` で作ったもの）に `.with` は付けられない。`not_to have_enqueued_mail(...).with(...)` と書く
- `rbs_rails:all` は触っていないモデルの生成物も列順を変えて書き直す。変えたモデルの分だけ残し、ほかは `git checkout` で戻す
- squash マージ後に main を作業ブランチへ取り込むと、新しく足したファイルが add/add で衝突する。中身は作業ブランチの方が新しいので `git checkout --ours` で解く
- Discord の HTTP は WebMock でスタブする。シークレットは `:discord` タグ（`spec/support/discord.rb`）で入れ、ほかの ENV は `with_env` で一時的に変える

## 残っている候補

- 型検査は `app/models` だけ。コントローラー・コンポーネントへ広げるのは次の候補
- `users#destroy` は画面から呼べないうえ、参加が `dependent: :nullify`（`user_id` は NOT NULL）、主催イベントの参加が `restrict_with_error` で実際には消せない（参加者のいるイベントの主催者だと `RecordNotDestroyed` で 500 になるはず。未確認）。退会を作るなら仕様から
- セッションはクッキーに `user_id` を持つだけなので、パスワードを再設定しても他の端末のログインは残る

- `Event#receive` は `RecordInvalid` も握りつぶすので、二重参加以外の検証エラーも「参加できませんでした」になる
- `Event.upcoming` / `.past` は `end_at` で分けるが、DB は `end_at` の NULL を許すので、NULL の行はどちらにも出ない（モデルでは必須）
- `ErrorNotifier` の間引きは `Rails.cache`（本番は既定のファイルストア）頼み。マシンが複数台になると台ごとに1通ずつ届く
- Litestream のコンテナは linux-x86_64 固定。arm64 の Mac で `docker compose build` すると使えないバイナリが入る（`BUCKET_NAME` が無ければ呼ばれない）
- .ics（#74）は `SEQUENCE` を出さない。日時変更後に取り込み直したとき、上書きされるかはカレンダーアプリ次第。中止理由も入れていない
- 参加費（`budget`）は文字列の列。詳細では数字だけなら「円」を付ける（#82）。一覧には開催場所と参加人数・満席を出す（#87）が、参加費は出していない
- 開催前日のリマインドは無い。定期実行の仕組み（Solid Queue の recurring など）が未導入なので、入れるなら基盤から
- 本番の Active Job は既定の async（プロセス内）。再起動・auto_stop・デプロイの前に積まれた DM や告知、429 の再試行待ちは消える。歓迎の DM の失敗も `Rails.cache`（ファイルストア）頼み
- 歓迎の DM を積むところで例外が出るとログインは 500 になり、次のログインでは新規ではないので歓迎の DM は二度と送られない（async では起きにくい）
- メールとパスワードのアカウントを持つ人が Discord でログインすると、紐づけずに別のユーザーができる。#95 で Discord に紐づかないユーザーは消す方針
- #95 は #93（オーナーが本番にシークレットを入れる）まで待つ。先に消すと本番で誰もログインできなくなる
- イベントをもとにした新規作成（#90）は内容を写すだけで、日時は空。翌月の同じ曜日などを入れる案や、繰り返しイベントは未着手
